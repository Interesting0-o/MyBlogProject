# 部署链路安全修复报告

日期：2026-11-27
范围：GitHub Actions 自动部署链路、Azure VM（vm-sudo4）服务器侧权限与脚本架构
结果：服务器侧迁移完成并验证通过；仓库侧待按第 8 节清单修改

## 1. 背景与原始故障

GitHub Action `Deploy production` 在部署阶段失败，报错：

```
sudo: a password is required
```

工作流通过 SSH 登录服务器后执行 `git pull`（成功），随后调用 `sudo -n ./scripts/deploy.sh "$tag"` 失败。`-n` 表示非交互模式，禁止询问密码。

直接诱因：为提升安全性，给服务器默认用户 `azureuser` 设置了 sudo 密码，导致 CI 非交互部署无法通过。

## 2. 根因分析

### 2.1 直接原因：sudoers 多条规则互相覆盖

排查发现 azureuser 的 sudo 权限由四条规则叠加定义：

```
(ALL : ALL) ALL                                    ← sudo 组（需密码）
(ALL) NOPASSWD: ALL                                ← 90-cloud-init-users（Azure 默认免密）
(root) NOPASSWD: /opt/sudo4/repo/scripts/deploy.sh ← sudo4-deploy（部署规则）
(ALL) ALL                                          ← waagent（需密码）
```

sudoers 机制：**多条规则匹配同一命令时，最后匹配的生效**；`sudoers.d` 按文件名字典序读取，`waagent` 排在最后。因此对部署脚本的匹配最终落在 waagent 的 `(ALL) ALL`（需密码）上，前面的 NOPASSWD 条目全部作废。

即：部署能否免密，长期依赖文件排序的巧合，而不是一条明确规则。

### 2.2 深层原因：root 执行的代码由部署用户可写的目录决定

原 sudoers 放行 `/opt/sudo4/repo/scripts/deploy.sh`，而 `/opt/sudo4/repo` 归部署用户可写（git pull 需要）。这带来两条提权/劫持路径：

1. **工作区脚本本地篡改**：`git pull --ff-only` 不还原本地未提交修改（无冲突时保留）。获得部署用户 shell 的人可直接编辑 deploy.sh，之后以 root 执行。此路径不经过 GitHub，分支保护无效。
2. **发布源劫持**：`fetch-release.sh` 每次运行时从 `.git/config` 的 `remote.origin.url` 解析仓库。该文件归部署用户可写，改为 fork 地址后，下载与 SHA256SUMS 校验均指向攻击者仓库，全部校验通过，恶意产物可进入服务与前端分发。

### 2.3 结构性问题：身份混用导致爆炸半径过大

人工管理（azureuser）与自动部署共用同一身份，部署私钥泄露 = 管理 shell = sudo = root。同时"CI 需要免密"与"管理账户需要密码"两个诉求在同一身份上不可调和。

## 3. 修复原则

1. **权限按角色拆分**：人工管理、自动部署、程序运行、Web 服务分别使用独立身份。
2. **root 只执行 root 拥有的代码**：部署用户只能决定"何时触发"，不能决定"root 执行什么内容"。
3. **密钥只存在于需要它的位置**：真实 `.env` 仅存放于 `/opt/sudo4/.env`（sudo4 拥有、600），不进 git、不在工作区留存。
4. **每个身份的权限只有一处定义**：不依赖 sudoers 覆盖顺序。

## 4. 目标架构（已落地）

### 4.1 用户角色

| 用户 | 职责 | 登录方式 | sudo 权限 | 失陷后果 |
|---|---|---|---|---|
| azureuser | 人工管理 | 个人私钥（ssh-rsa，Azure 注入） | 全量，需密码 | 严重，但已脱离 CI 链路 |
| deploy | GitHub Action 专用 | 部署专用私钥，禁止密码登录 | 仅 `NOPASSWD: /opt/sudo4/deploy/deploy.sh` | 普通用户 + 可拉代码 + 可触发部署，无法提权 |
| sudo4 | 运行后端 | nologin | 无 | 限于应用本身 |
| www-data | nginx worker | nologin | 无 | 限于 Web 服务 |

### 4.2 目录与权限

```
/opt/sudo4/                     root:root      755
├── deploy/                     root:root      755   ← root 唯一代码来源
│   ├── deploy.sh               root:root      755
│   └── fetch-release.sh        root:root      755
├── repo/                       deploy:deploy  755   ← 仅代码来源（git pull）
├── releases/                   root:root      755   ← 仅 root 部署脚本写入
├── current -> releases/...     root                 ← 原子切换
├── backups/                    root:root      700   ← 数据库备份
├── resource/                   sudo4:sudo4    750   ← SQLite 数据目录
└── .env                        sudo4:sudo4    600   ← 真实密钥唯一存放点
```

## 5. 服务器侧已执行变更

### 5.1 SSH 加固

- 发现 cloud-init 注入的 `/etc/ssh/sshd_config.d/50-cloud-init.conf` 中 `PasswordAuthentication yes` 覆盖了主配置。
- 新建 `/etc/ssh/sshd_config.d/00-hardening.conf`（sshd 配置先出现先生效，`00-` 前缀确保优先）：

```
PasswordAuthentication no
PermitRootLogin no
```

- `sshd -t` 校验后 reload，`sshd -T` 实测两项均已生效。
- root 的 authorized_keys 仅含 Azure 占位公钥（forced command 拒绝登录），无风险。

### 5.2 sudoers 清理

- 注释掉 `/etc/sudoers.d/90-cloud-init-users` 中的 `azureuser ALL=(ALL) NOPASSWD:ALL`。
- 删除旧的 `/etc/sudoers.d/sudo4-deploy`（azureuser 的部署免密条目）。
- 保留 `waagent`（Azure 代理管理，内容为需密码的全量 sudo）与 sudo 组规则。
- 新建 `/etc/sudoers.d/deploy`（440）：

```
deploy ALL=(root) NOPASSWD: /opt/sudo4/deploy/deploy.sh
```

### 5.3 部署用户与密钥

- 创建 `deploy` 用户：`adduser --disabled-password`（禁止密码登录，非免密登录），不在 sudo 组。
- 生成 ed25519 专用密钥对（comment: `github-actions-deploy`），公钥安装至 `/home/deploy/.ssh/authorized_keys`（700/600）。
- 本机 SSH 验证通过：`ssh -i /tmp/deploy_key deploy@localhost 'id'` 返回 `uid=1001(deploy)`。
- 迁移完成后：azureuser 的 authorized_keys 仅保留 ssh-rsa 管理公钥，两把 ed25519 部署公钥已删除；临时私钥文件已 `shred` 销毁；旧部署私钥在所有位置失效。

### 5.4 脚本迁移与修改

两个脚本从 `/opt/sudo4/repo/scripts/` 复制到 `/opt/sudo4/deploy/`（root:root 755），修改如下。

**deploy.sh**：

```diff
-script_dir="$(cd -- "$(dirname -- "${BASH_SOURCE[0]}")" && pwd)"
-repo_root="$(git -C "$script_dir" rev-parse --show-toplevel)"
+repo_root=/opt/sudo4/repo

-DEST="$staging" "$repo_root/scripts/fetch-release.sh" "$tag"
+DEST="$staging" /opt/sudo4/deploy/fetch-release.sh "$tag"
```

**fetch-release.sh**：

```diff
-script_dir="$(cd -- "$(dirname -- "${BASH_SOURCE[0]}")" && pwd)"
-repo_root="$(git -C "$script_dir" rev-parse --show-toplevel)"
+repo_root=/opt/sudo4/repo

-# 整段 GITHUB_REPOSITORY / remote.origin.url 检测逻辑（含 case 分支与格式校验）
+repo="Interesting0-o/MyBlogProject"

# read_git_proxy 中删除对 repo local config 的读取：
-value="$(git -C "$repo_root" config --get "$key" 2>/dev/null || true)"
-if [[ -n "$value" ]]; then ... fi
# 仅保留从 SUDO_USER 个人 gitconfig 读取代理的部分
```

修改要点说明：

- `repo_root` 固定路径仅用于 `.artifacts` 默认输出目录与代理读取；新位置不在 git 仓库内，原来的 `git rev-parse` 推导会在 `set -e` 下直接导致脚本退出，必须移除。
- 发布源硬编码后，`.git/config` 篡改无法影响下载地址；同时避免 root 对 deploy 拥有的仓库执行 git 触发 `dubious ownership`。
- 备份、原子切换、健康检查、失败回滚、旧版本清理逻辑未改动。

### 5.5 仓库属主移交

```
chown -R deploy:deploy /opt/sudo4/repo
sudo -u deploy git -C /opt/sudo4/repo pull --ff-only   # 验证通过
```

工作区残留的 `repo/.env` 已清理（该文件从未被 git 追踪，git 历史无泄露）。

## 7. 修复后威胁路径对照

| 攻击路径 | 修复前 | 修复后 |
|---|---|---|
| 篡改工作区 deploy.sh 后以 root 执行 | 可行（git pull 不还原本地修改） | root 不读工作区文件，无效 |
| 篡改 .git/config 劫持发布源 | 可行，校验全部通过 | 发布源硬编码，无效 |
| 部署私钥泄露 | azureuser → sudo → root | 普通用户 + 可触发部署，无法提权 |
| 恶意 PR 合入 main | 由分支保护阻断 | 不变 |
| release 产物被替换 | 需能 push main | 信任根收束到分支保护 + HTTPS + SHA256 |
| azureuser 失陷 | root | 仍是管理账户，靠个人密钥管理与禁用密码登录独立防护 |

## 8. 仓库侧待修改清单

### 8.1 `.github/workflows/deploy.yml`

远端部署命令改为新路径（其余不变）：

```diff
- sudo -n ./scripts/deploy.sh "$tag"
+ sudo -n /opt/sudo4/deploy/deploy.sh "$tag"
```

GitHub Secrets 同步更新：

- `DEPLOY_USER` → `deploy`
- `DEPLOY_KEY` → 新部署私钥的 base64（单行，`base64 -w0` 生成）
- `DEPLOY_HOST` → 不变

完成后手动 `workflow_dispatch`（tag=`latest`）做一次验收。

### 8.2 `scripts/` 脚本回收

将服务器上 `/opt/sudo4/deploy/` 的两个最终版脚本拷回，替换仓库 `scripts/deploy.sh`、`scripts/fetch-release.sh`，保持仓库为脚本单一事实源。`repo_root` 固定路径对 `post-merge` hook 的本地使用场景同样适用。

### 8.3 `docs/deployment.md` 需更新的段落

- **2.6 节**：sudoers 示例替换为 `deploy ALL=(root) NOPASSWD: /opt/sudo4/deploy/deploy.sh`；说明 azureuser 仅作人工管理、sudo 需密码。
- **用户与目录说明**：补充 deploy / sudo4 / www-data 角色表与目录属主表（见本报告第 4 节）。
- **部署命令**：所有 `sudo ./scripts/deploy.sh` 改为 `sudo /opt/sudo4/deploy/deploy.sh`。
- **脚本变更流程**：仓库 PR 合并后，需手动 `sudo cp` 同步到 `/opt/sudo4/deploy/`——此步骤即 root 执行权的人工审批点。
- **排障表新增**：
  - Action 报 `sudo: a password is required` → 检查是否仍在使用旧用户（azureuser）或旧路径（repo/scripts）。
  - 部署脚本启动即退出 → 检查是否残留 `git rev-parse` 位置推导（/opt/sudo4/deploy 不在 git 仓库内）。
  - 健康检查 curl 失败 → 确认端口 3000、路径 /health。
  - root 执行 git 报 `dubious ownership` → 不应再出现；出现即说明有脚本残留对 repo 的 git 调用。
- **密钥管理**：记录本次密钥换防流程（新通道验证通过后再吊销旧公钥；吊销本体 = 删除服务器 authorized_keys 中的公钥，覆盖 GitHub secret 只是删除一份副本）。

## 9. 后续维护规程

日常运维只需记住：

```bash
systemctl status sudo4-api                          # 服务状态
curl -fsS http://127.0.0.1:3000/health              # 健康检查
sudo /opt/sudo4/deploy/deploy.sh latest             # 手动部署（azureuser，输密码）
sudo /opt/sudo4/deploy/deploy.sh <tag>              # 部署/回滚到指定版本
journalctl -u sudo4-api                             # 服务日志
```

脚本变更流程：仓库修改 → PR review 合并 → 手动同步 `sudo cp repo/scripts/*.sh /opt/sudo4/deploy/` → 按需部署。

密钥轮换：生成新密钥对 → 安装 deploy 公钥 → 验证登录 → 覆盖 GitHub DEPLOY_KEY → Action 验证 → 删除旧公钥。

## 10. 可选增强（未实施，按需）

- **第三方 Action 钉 commit SHA**：`uses: actions/checkout@<完整 sha>`，防上游 tag 被重写。
- **production environment 加 required reviewers**：workflow_dispatch 也需人工批准。
- **deploy 用户 forced command**：authorized_keys 挂命令白名单，进一步压缩为仅可 git pull 与触发部署。
- **systemd 单元加固**：`NoNewPrivileges=true`、`ProtectSystem=full`、`PrivateTmp=true` 等。
- **tar 解压加 `--no-same-permissions`**：优先级低，产物来源可信。
